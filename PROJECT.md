# DərsReport — обзор проекта

Этот файл — точка входа для нового Claude Code (или любого разработчика),
который впервые открывает репозиторий: что за проект, как он устроен и на
что обращать внимание.

Если что-то здесь разошлось с реальным кодом — верь коду, а не этому файлу,
и поправь файл заодно.

---

## Что это за проект

**DərsReport** ("Lesson Report") — приложение для управления репетиторским
центром: учителя ведут учеников, расписание и отчёты об уроках; родители
и ученики видят прогресс в реальном времени; администрация (Boss/Admin)
управляет учителями, расписанием и финансами по всей организации.

- **Стек**: Expo (React Native) + Firebase (Firestore, Auth, Cloud
  Functions v2). Монорепо: мобильное приложение в `apps/mobile/`,
  серверный код в `functions/`.
- **Платформы**: iOS и Android через Expo Go / Development Build.
- **Firebase project ID**: `dersreport` (см. `.firebaserc`).
- **GitHub**: `https://github.com/Nagiev217/dersreport` (remote `origin`,
  ветка `master`).
- **Разработчик проекта**: один человек (владелец репетиторского центра),
  не профессиональный программист — работает через Claude Code.

## Роли в приложении

Пять ролей, у каждой свой набор вкладок (`(xxx-tabs)` в
`apps/mobile/src/app/`):

| Роль | Папка экранов | Кто это |
|---|---|---|
| `teacher` | `(tabs)/` | Репетитор — ведёт своих учеников, уроки, отчёты |
| `parent` | `(parent-tabs)/` | Родитель — видит прогресс своего ребёнка |
| `student` | `(student-tabs)/` | Сам ученик, если у него есть аккаунт |
| `admin` | `(admin-tabs)/` | Администратор — управляет расписанием и оплатами по всем учителям |
| `boss` | `(admin-tabs)/` (тот же UI, другие права) | Владелец — видит всё, включая финансы/зарплаты учителей |

Роль хранится в `users/{uid}.role`, читается через `getMyRole` /
`requireStaffCaller` на сервере. **Важный факт архитектуры**: Boss и Admin
могут сами преподавать — первый тайл в Quick Access ("Обучение") ведёт их
в `/(tabs)`, то есть они легитимно владеют `teachers/{ihUid}/...` данными
наравне с обычными учителями.

## Модель данных (Firestore)

Верхнеуровневые коллекции: `users`, `teachers`, `parents`, `students`,
`parentCodes`, `studentCodes`, `parentAccess`, `studentAccess`.

**Учительские данные** — паттерн "весь массив в одном документе":
`teachers/{uid}/stores/{storeName}` = `{ data: [...], ts }`, перезаписывается
целиком (`merge: false`) при каждом изменении. Имена сторов: `students`,
`lessons`, `payments`, `schedules`, `progress`, `groups`, `parents`,
`homework`, `writing`, `exams`.

**Исключение — `reports`**: мигрированы на подколлекцию
`teachers/{uid}/reports/{reportId}`, один документ на отчёт (у старой
whole-array схемы было ограничение 1MB на документ, отчёты за пару лет его
пробивали).

**Связи родитель/ученик ↔ учитель**: `parentAccess/{parentUid}/teachers/{teacherUid}`
= `{ studentIds: [...], teacherName, linkedAt }`. Аналогично
`studentAccess/{studentUid}/teachers/{teacherUid}` = `{ studentId, ... }`
(у ученика один id, не массив). Пишет только учитель (владелец), читает
только сам родитель/ученик — так устроены Firestore rules.

**Ключевой факт про типы полей**: `studentId` в отчётах и связках **всегда
должен быть строкой** (`String(id)`). Раньше был баг с генерацией id вида
`String(Date.now())` без соли — коллизии на одинаковой миллисекунде ломали
React-ключи. Исправлено: id теперь `` `${prefix}-${Date.now()}-${Math.random().toString(36).slice(2,8)}` ``.
Такой формат применён во всех местах генерации id (ученики, отчёты, уроки,
расписания, платежи и т.д.) — если добавляешь новое место генерации id,
используй тот же паттерн.

## Синхронизация клиент ↔ Firestore

Учительский клиент (`apps/mobile/src/app/_layout.jsx`, хук
`useFirebaseSync`) при входе:
1. Загружает все сторы одним запросом (`loadAllStores`).
2. Подписывается на **живые изменения** (`onSnapshot`) для сторов, которые
   может писать не только сам клиент — сейчас это `lessons`, `schedules`,
   `payments` (их пишет и Cloud Functions при действиях Admin). Остальные
   сторы пишет только сам клиент, поэтому живой listener для них не нужен.
3. При локальном изменении — debounced-запись обратно в Firestore
   (`students`/`lessons` — мгновенно, остальное — с задержкой 1.5с).

Родители и ученики читают данные учителя напрямую через
`utils/firebase/parentRealtime.js` / `studentRealtime.js` — отдельные
`onSnapshot`-подписки на `teachers/{uid}/stores/{name}` (только `students`,
`lessons`, и у ученика ещё `progress`, `exams`) плюс query по
`reports`-подколлекции с фильтром `where("studentId","in",[...])`.

**Известное ограничение (не баг, задокументировано в `firestore.rules`)**:
`students` и `lessons` — целые документы-массивы, Firestore не умеет отдавать
их частично. Родитель, подписавшись на такой стор, физически получает
данные *всех* учеников этого учителя, не только своих — клиент фильтрует
на своей стороне. Закрыть полностью можно только миграцией этих сторов на
подколлекции, как уже сделано для `reports`. Это big-scope задача, не
начата.

## Серверная часть — Cloud Functions (`functions/index.js`)

Все функции — `onCall`, гейт через `requireStaffCaller(request, ['boss','admin'])`
(проверяет `users/{uid}.role` **и** `users/{uid}.disabled`, отклоняет
отключённые аккаунты — токен Firebase Auth сам по себе не инвалидируется
мгновенно при disable, поэтому проверка нужна и на сервере).

Полный список функций (23 штуки), сгруппированы по смыслу:

- **Аккаунты** (Boss-only): `createManagedAccount`, `setAccountEnabled`,
  `resetManagedPassword`, `deleteManagedAccount`
- **Роль**: `getMyRole` (публичная, читает свою же роль)
- **Списки/агрегаты** (Boss+Admin): `listManagedTeachers`,
  `listManagedParents`, `getManagedTeacherStores`, `getOrgAnalytics`,
  `getOrgActivity`, `getTeacherWorkload`
- **Финансы студентов** (Boss+Admin, новое): `getStudentPayments`,
  `addStudentPayment`, `deletePayment` — кто оплатил/не оплатил за месяц
- **Финансы/зарплаты** (Boss-only): `getFinanceOverview`,
  `getMonthlyPaymentsExport`, `setTeacherSalary`, `getPayroll`
- **Расписание** (Admin-only, кроме чтения): `adminCreateTeacherSchedule`,
  `adminUpdateTeacherSchedule`, `adminDeleteTeacherSchedule`,
  `getOrgSchedule` (Boss+Admin читают)
- **Триггер**: `onReportCreated` — при создании отчёта шлёт push родителю/ученику
  через Expo push API

Все мутации, затрагивающие массив (`addStudentPayment`, `deletePayment`,
`admin*Schedule`), обёрнуты в `db.runTransaction` — без этого конкурентные
вызовы могли молча затирать друг друга (read-modify-write race на одном
документе).

## Права доступа — кто что видит

Разграничение в `apps/mobile/src/utils/auth/permissions.js`:
- `canViewFinance` — только Boss (зарплаты/payroll учителей)
- `canViewPayments` — Boss + Admin (платежи учеников — операционные данные,
  не зарплаты, поэтому отдельное право)
- `canManageAccounts` — только Boss (создание аккаунтов)
- `canManageSchedules` — только Admin (**намеренно не Boss** — продуктовое
  решение: Boss расписания не редактирует)

## i18n

Три локали в одном файле: `apps/mobile/src/utils/i18n/translations.js`,
объекты `ru`, `az`, `en` в этом порядке (примерно по 1000+ строк каждый).
**Важно**: файл в CRLF-переносах строк — при программной правке (не через
Edit tool) регулярки с `\n` не сработают, нужно расщеплять по `/\r?\n/`
и склеивать обратно с тем же EOL.

Правило: любой новый пользовательский текст добавляется **во все три
локали сразу**. Проверка — `grep -c "^  keyName:" translations.js` должно
быть `3`.

## Дизайн-система

Единый стиль **Blue + Indigo + White** на большинстве экранов. Токены не
вынесены в общий файл — они переобъявлены константами вверху каждого
экрана (искать `const BLUE = "#2563EB"` и рядом), так исторически сложилось.
При правке экрана бери значения именно из него, не выдумывай — они должны
совпадать один в один с этим списком:

```
BLUE      #2563EB   — основной акцент, primary-кнопки, активные состояния
INDIGO    #4F46E5   — вторичный акцент, обычно вперемешку с BLUE
BLUE_50   #EFF6FF   — фон плашек/иконок на BLUE-акценте
INDIGO_50 #EEF2FF   — фон плашек/иконок на INDIGO-акценте
TEXT      #111827   — основной текст
SUB       #8E93A1   — вторичный текст, подписи, лейблы
BORDER    #E5E9F2   — обводка карточек и разделители
```
Плюс несколько повторяющихся не-брендовых акцентов для статусов/категорий
(зелёный `#16A34A`/`#ECFDF5` — success/посещаемость, янтарный
`#D97706`/`#FFFBEB` — оценки/предупреждения, красный `#EF4444` — badge
непрочитанного). Их тоже стоит переиспользовать, а не подбирать новые
оттенки на глаз.

**Типографика**: только шрифты Inter, подключены четыре начертания —
`Inter_400Regular`, `Inter_500Medium`, `Inter_600SemiBold`, `Inter_700Bold`
(загружаются в `apps/mobile/src/app/_layout.jsx` через `useFonts`). Другие
шрифты/начертания не использовать. Примерная шкала размеров по факту
использования: `11-13` — мелкие подписи/метки, `14-15` — основной текст
карточек, `16-18` — заголовки секций/имена, `24-28` — крупные цифры
статистики и приветствие на дашборде. Заголовки обычно с небольшим
отрицательным `letterSpacing` (`-0.2` … `-0.6`) — это часть стиля, не
случайность.

**Карточки**: `borderWidth: 1, borderColor: BORDER`, тени НЕ используются
(единственное исключение — статистические карточки, у них лёгкая
индиговая тень). Радиусы скругления по факту использования: `10-13` —
мелкие элементы (иконки-плашки, кнопки), `18-20` — обычные карточки-секции,
`22+` — крупные акцентные карточки (например карточка ребёнка на
дашборде родителя). Круглые элементы (аватары) — `borderRadius` строго
в половину стороны.

**Отступы**: 8pt-сетка, кратно 4. На дашборде родителя формализовано в
объект `const S = { xs: 4, sm: 8, md: 12, lg: 16, xl: 24 }` — если
переписываешь другой экран под этот стиль, заведи такой же объект вместо
голых чисел.

**Иконки**: только `lucide-react-native`, никаких эмодзи как иконок и
никаких растровых картинок для UI-элементов. Размер иконки внутри цветной
плашки обычно `16-20px` при плашке `32-40px`.

**Интерактив**: тап-фидбек — общий компонент `PressableScale`
(`apps/mobile/src/components/PressableScale.jsx`), пружинная анимация
через Reanimated (`dampingRatio`, не duration — так предсказуемее ведёт
себя при повторном тапе во время анимации). Используется вообще везде,
где что-то тапается — не изобретай свой `TouchableOpacity` с ручной
анимацией, оборачивай в `PressableScale`.

**Повторяемые паттерны компонентов** (см. `(parent-tabs)/index.jsx` как
эталон): `SectionCard` — карточка-секция с заголовком и опциональной
ссылкой «Смотреть все →» справа; `StatCard` — квадратная карточка
статистики с цветной иконкой сверху, крупным числом и подписью. Если на
новом экране нужна секция с заголовком или блок статистики — проверь,
не проще ли скопировать эти компоненты, а не писать заново.

**Не всё ещё переведено на этот стиль.** Есть тестовые
экраны-варианты, между которыми решение ещё не принято:
- `(parent-tabs)/child.jsx` vs `child-variant-modules.jsx`
- `(parent-tabs)/reports.jsx` vs `reports-variant-timeline.jsx`
- `(admin-tabs)/analytics.jsx` vs `analytics-variant-calm/premium/tabs.jsx`

Экраны-варианты зарегистрированы в `_layout.jsx` с `href: null` (скрыты
из таб-бара, доступны только по прямой навигации/сравнению).
`(parent-tabs)/index.jsx` (дашборд родителя) уже переписан на новый стиль
целиком с реальными данными (не мок) — лучший референс для нового экрана.

**При запросах на дизайн/редизайн** в проекте подключён скилл
`ui-ux-pro-max` (`.claude/skills/ui-ux-pro-max`). Важно: его команда
`--design-system` даёт общие рекомендации без учёта уже принятого стиля
проекта — при работе над существующим приложением приоритет всегда за
консистентностью с Blue+Indigo+White выше, а не за тем, что предложит
скилл с нуля. Чек-лист скилла (touch target ≥44pt, контраст, safe area,
никаких эмодзи-иконок) при этом стоит применять всегда.

## Инструменты и процессы, которые уже настроены

- **Проверка синтаксиса** после любых правок:
  ```
  node --check functions/index.js
  ```
  и Babel-компиляция всех `apps/mobile/src/**/*.{js,jsx}` (~130 файлов) —
  скрипт через `require('@babel/core').transformFileSync`, `cwd` должен
  быть `apps/mobile/` чтобы подхватился `babel.config.js` с плагином
  worklets.
- **Деплой функций**: `firebase deploy --only functions:<name1>,<name2>`.
  На этой машине первая попытка почти всегда падает с транзиентной
  ошибкой `Cannot determine backend specification. Timeout after 10000` —
  повторный запуск сразу после обычно проходит.
- **Тестирование Firestore rules без прод-доступа**: поднят изолированный
  тестовый проект в scratchpad с `@firebase/rules-unit-testing` +
  Firestore emulator. Для эмулятора нужна **JDK 21+** — на этой машине
  штатная Java была 1.8, рабочая JDK 21 нашлась в составе Android Studio:
  `C:\Program Files\Android\Android Studio\jbr`. Не забыть выставить
  `$env:JAVA_HOME` перед `firebase emulators:exec`.
- **Запуск приложения**: `cd apps/mobile && npx expo start --tunnel` (или
  без `--tunnel` в общей Wi-Fi сети — быстрее и надёжнее). После правок в
  `babel.config.js` или зависимостях — обязательно с `--clear`, иначе Metro
  отдаёт закэшированную (уже неактуальную) трансформацию.

## С чем нужно быть осторожным при работе с этим пользователем

- Не программист, объясняй находки простым языком, без прыжков через
  технические термины без контекста.
- Просит подтверждение перед вещами, которые сложно отменить (пуш на
  GitHub, удаление файлов, апгрейды зависимостей, деплой в прод) — но при
  этом ценит, когда решение принимается автономно там, где выбор
  очевиден, а не переспрашивается по мелочам.
- Любит, когда сначала диагностируют факт (тестом/логами/чтением кода), а
  не гадают — несколько раз в истории именно гипотеза "на глаз" уводила в
  сторону, и только конкретная проверка (сборка бандла, тест правил на
  эмуляторе) находила настоящую причину.
